### 1.7 턴수 분포 — 하드 상한(설계) + 매 턴 종료확률로 도출
본 서비스는 **최대 턴 상한**을 건다(설계 결정): 턴이 쌓이면 ① 컨텍스트 히스토리 누적으로 prefill/TTFT↑ ② 멀티턴 품질 저하로 CX 악화. 따라서 분포는 **자연 종료확률을 상한에서 절단**한 형태다. **절단은 피팅 artifact가 아니라 제품 제약** → E[T]가 ShareChat 무절단 평균(2.31왕복)보다 짧은 건 **의도된 결과**. **턴 정의: 1턴 = triage+answer 1왕복(유저1+봇1 = 2발화).**

**(A) 상한 T_max — 리서치 근거로 5턴 권장:**

| 근거 | 내용 | 함의 |
|---|---|---|
| 시스템 히스토리 창 | triage 히스토리 **최근 5턴 캡**(§1.3) | 5턴 초과 시 초기 맥락 드롭 → 봇이 앞부분을 '잊은' 채 답 → 더 끌 이유 없음 |
| 멀티턴 품질 저하 | Laban 2025: 멀티턴 정확도 **−39%**, 신뢰성 **+112% 악화**, "틀리면 회복 못 함" | 5턴이면 품질 훼손 → 이관 |
| Latency | 짧은 멀티턴은 **prefill이 체감지연 ~84%**(4K prefill 15.7s) | 턴↑=컨텍스트↑=TTFT↑ → 상한 필요 |
| 이관 베스트프랙티스 | 2~3회 실패 시 이관, **45% 3회 실패 후 이탈** | 5는 권고(2~3)보다 여유 있는 hard ceiling |

→ **T_max=5**(히스토리 창과 일치). 타이트(3~4)면 지연·품질↑이나 컨테인먼트↓(이관↑→인건비↑) — 트레이드오프는 (D).

**(B) 매 턴 종료확률 h_k (자연 종료율; 각 확률의 근거):**

| 턴 k | h_k | 근거 |
|---|---|---|
| 1 | 0.50 | 단답 FAQ 해결 + 즉시 사람요청. KB: 복잡문의 **54% 즉시 상담원**, **73.6% "AI가 못 알아들음"**. ShareChat 중위=1왕복 → 1턴 종료 ~50% |
| 2 | 0.50 | 1회 해명 후 해결 / 1차 실패 후 이관. KB 의도오인식 23% |
| 3 | 0.50 | 베스트프랙티스 2~3회 이관, 45% 3회 실패 후 이탈 |
| 4 | 0.50 | 잔여 |
| 5 | **1.00** | **하드 상한** — 히스토리 창 소진·−39% 품질·지연 → 강제 이관 |

> h를 ShareChat **평균(2.31)이 아니라 초기거동(중위=1왕복→h≈0.5)**에 앵커하는 이유: 상한 5로 **긴 꼬리를 잘라내므로**, 꼬리가 부풀린 평균이 아니라 앞 턴들의 종료율이 옳은 기준.

**(C) 계산 (생존확률):**
```
P(1)=h            = 0.500
P(2)=(1−h)·h      = 0.250
P(3)=(1−h)²·h     = 0.125
P(4)=(1−h)³·h     = 0.0625
P(5)=(1−h)⁴       = 0.0625   (상한이라 잔여 전부 종료)
E[T] = 1(.5)+2(.25)+3(.125)+4(.0625)+5(.0625) = 1.94
```

| P(T) | 0.500 | 0.250 | 0.125 | 0.0625 | 0.0625 | **1.94** |

## 5. 자체호스팅 GPU 사이징 (H100 SXM, Qwen3.5/3.6-35B-A3B)

### 5.1 원리 — prefill + decode 부담을 **둘 다** 더한다
입력이 출력의 ~11배(prefill-heavy)라 출력만 보면 안 됨. GPU는 prefill(입력 처리)과 decode(출력 생성)에 시간을 나눠 씀:
```
GPU 부담 = 피크입력 ÷ prefill_capacity  +  피크출력 ÷ decode_capacity
피크 = 일일토큰 × BHF ÷ 3600   (BHF=분주시율, 기본 0.17 / 보수 0.20)
```
> **피크배수→분주시율(BHF) 교체:** 기존 "영업 9h·피크배수 2"는 분주시간에 일일콜의 22%가 몰린다는 무근거 가정이었다. 통신/콜센터 트래픽 표준은 **분주시율 17%**(8h 영업일 Erlang 기본값; 보수 20%)로, 일일토큰의 17%가 가장 바쁜 1시간(3,600초)에 인입한다고 본다. 즉 분모 = 3600÷0.17 = **21,176초**(기존 16,200보다 덜 보수적 = 과프로비저닝 해소). 하나카드 영업시간대(오전·오후 2-peak) 실측으로 확정.

### 5.2 성능 앵커 — **직접 측정** (Millstone AI, Qwen3.5-35B-A3B FP8, 1×H100 SXM)
| 지표 | 값 |
|---|---|
| decode 단일스트림(1K ctx) | **212.2 tok/s** |
| decode 집계 @동시10(1K) | **907.7 tok/s** (1인당 90.8) |
| prefill @동시1(8K) | **57,296 tok/s** (동시5: 53,786) |
| TTFT(1K) | 111ms |

> 출처: millstoneai.com (qwen3-5-35b-a3b-fp8-1x-h100-sxm). **타깃과 동일 아키텍처(35B-A3B)·동일 GPU(H100 SXM) 직접 측정** → 프록시·GPU 스케일링 오차 없음. 컨텍스트 1K는 우리 ~1.6K와 사실상 동일(decode 1K→8K −5%).

### 5.3 사이징 capacity (보수 채택)
```
decode_capacity = 907.7 tok/s   (측정된 SLO-충족 운영점, §5.4)
prefill_capacity = 50,000 tok/s  (실측 53,786~57,296 보수 절삭)
```

### 5.4 SLO 임계와 decode 집계 (방법)
**SLO 임계 = 고객 1인당 최소 decode 속도** = (턴 SLO − 오버헤드) ÷ decode토큰:
```
텍스트: (5초 − 0.8초) ÷ 149 = 35.5 → 여유분 40 tok/s
음성:   (4초 − 2.0초) ÷ 149 = 75, p95(172토큰) 86 tok/s   (§7)
```
**capacity 산정 = 외삽 대신 측정점 채택:** 동시10에서 1인당 90.8 tok/s ≥ 임계(40~86) → SLO 충족 **증명** → 집계 907.7을 capacity로 채택(보수, 외삽 없음).
- 상방(부하테스트 시): 2점 모델 `T_step=4.01+0.700·B`(c=1,10 피팅, c=10 예측 907.7 검증✓)로 1인당 40까지 올리면 집계 ~1,200 → GPU 한 단계↓ 여지.

피크 = 일일토큰×BHF÷3600. 기본=E[T]1.94·BHF0.17, 보수=T3·BHF0.20. 24/7 상주, N+1 HA.

### 5.7 GPU 월 단가 — 온프레미스 TCO (클라우드 렌탈 비채택)

클라우드 렌탈($2.5/hr→$1,800/GPU·월)은 **공급사 마진 포함 상한**이고, 본 시스템의 도입 동기(PII 국외이전 차단·망분리)와 어긋나며 장기 위험이 크다. 따라서 단가는 **온프레미스 자가운영 TCO**로 산정하고, GPU SKU는 직접 벤치한 **H100 SXM을 기준**으로 두되 H200으로 **갈아끼우기 쉽게** 파라미터화한다.

**GPU 1장당 월 TCO (H100 SXM, 자가운영):**
| 항목 | 금액/GPU·월 | 산근거 |
|---|---|---|
| capex 상각 | **$972** | 8-GPU HGX 노드 ~$280K(Arc $210K~인프라포함 $400K) → $35K/GPU, **3년(36개월)** 상각. 4년=$729·5년=$583 |
| 전력+냉각 | **$170** | 노드 ~10.2kW/8 = **1.28kW/GPU**(IT), PUE 1.4 → 1.78kW × 730h × **$0.133/kWh**(한국 산업용 ₩180/kWh) |
| 유지보수·지원·랙·네트워크 | **$150** | OEM/NVIDIA 지원 ~5%/yr + DC 공간·패브릭 상각 |
| **합계 (3년 상각)** | **≈ $1,300** | 4년 상각 시 ~$1,050 · 5년 ~$900 |

- **capex가 TCO의 ~75%를 지배.** 전력은 ~13%라, 한국 전력 프리미엄(₩180/kWh, UAE 73·말레이 60~100 대비 2배+)은 실재하나 TCO 영향은 제한적 — **핵심 레버는 상각연수·가동률**(피크 사이징이라 off-peak 유휴).
- **H200 스왑:** capex ~$46K/GPU → 상각 3년 $1,278 + 전력 $170 + 지원 $190 = **~$1,640/GPU·월**, decode ~1,200(대역폭 4.8TB/s). E[T]=1.94에선 H200 부담 0.93<1이라 기본 1+HA 2장=$3,280으로 H100(2+HA 3장=$3,900)보다 근소 저렴 가능 — 단 단일 GPU 93% 피크가동은 시간내 버스트 여유가 없어 위험. **실 compute 수요가 ~1장이라 대수는 throughput이 아니라 HA·헤드룸 정책이 좌우**; 안전 디폴트는 H100 2+HA 3장.
- (참고·비추천) 클라우드 렌탈 $1,800/GPU·월 기준이면 동일 장수에서 온프레미스보다 ~38% 비쌈.

**월 GPU 비용 = 장수 × $1,300:**

## 7. 음성(STT/TTS) 포함 SLO — decode 임계가 올라감

현재 비스트리밍 파이프라인: `음성 E2E = STT + [rerank+검색+prefill+decode] + TTS` (직렬).
```
STT(VITO) ~1.0초 + 워크플로우 비-decode ~0.3초 + TTS(Google) ~0.7초 ≈ 고정 2.0초
decode 예산 = E2E SLO − 2.0초
```
| 음성 E2E | decode 예산 | 1인당 임계(p95 172토큰) | decode 집계 | 비고 |
|---|---|---|---|---|
| 3초 | 1.0초 | 172 | ~440 | **비스트리밍 불가**(단일 212 근접) |
| **4초(권장)** | 2.0초 | **86** | **~907** | 측정점 c=10(90.8)이 턱걸이 충족 |
| 5초 | 3.0초 | 57 | ~1,100 | 여유 |

- **음성 포함 시 임계 40 → 86(E2E 4초)로 2배 상승**, decode 집계 1,200 → ~907(=§5 보수값과 수렴).
- **E2E 3초(자연스러운 음성)는 비스트리밍 불가** → **문장단위 스트리밍 TTS(P1-8)**가 핵심 레버(TTS ~0.7초를 critical path에서 제거).
- STT/TTS 지연은 추정 → **실측 필요**.

## 8. 원가 산정 추가 고려 요소 (LLM 토큰비를 압도)

**C. 모델 리스크** — Thinking OFF 고정(켜지면 출력 ×10–50), 재시도 +2–5%, o200k 토크나이저 ±15%, KV캐시 제약.

**D. 운영·재무** — 성장/피크 헤드룸, 카테고리 분포(R·h), 데이터·평가 유지보수, 컴플라이언스 인증, FX.

## 11. 한 줄 결론

**Qwen3.6-35B-A3B를 H100 SXM에 온프레미스 자가운영하면, 하드 상한 5턴 E[T]=1.94·분주시율 17%에서 GPU(+HA) 2+HA=3장 → 월 ~$3,900**(decode 907.7·prefill 50,000·온프레미스 TCO $1,300/GPU·월=capex 3년상각+한국 전력+PUE1.4)으로, **gpt-4o-mini API($1,165)보다 ~3.3배 비싸다**(보수 T=3에선 4장 $5,200 vs $1,697로 ~3배). 따라서 로컬 전환은 **컴플라이언스 결정**이며, 원가의 진짜 지배 요인은 **핸드오버 30%의 상담사 인건비와 음성 I/O**다. GPU 대수는 사실상 **decode 처리량(907.7)**이 결정하고, 단가는 **클라우드 렌탈이 아니라 온프레미스 TCO**로 잡되 H100↔H200을 갈아끼울 수 있게 둔다(H100 우위). 확정 변수: 턴수 히스토그램·분주시율·decode 907.7↔1,200·GPU 조달가/상각연수.
